## 2. Назначение и цели

Модуль IR-Bridge фиксирует каждую успешную валидацию на валидаторах с IntelliReader и передаёт её в CAMAI для сопоставления с числом вошедших пассажиров. Модуль не вмешивается в работу АСОП и не отправляет команд в IR.

**Цели**

1. Получать событие по каждой успешной валидации с привязкой к валидатору, двери, времени и типу носителя.
2. Рассчитывать число предположительно безбилетных пассажиров по остановкам, рейсам и суткам.
3. Фиксировать отказы в валидации и неисправности валидаторов, чтобы не считать безбилетниками пассажиров, вошедших при неработающем валидаторе.

**Расчётная величина.** Для интервала учёта *i* (стоянка на остановке плюс настраиваемый хвост перегона, по умолчанию 120 с):

```latex
N^{\text{безб}}_i = \max\Bigl(0,\; N^{\text{вош}}_i - \sum_{v \in i} k_v\Bigr)
```

где Nвош — число вошедших по данным счётчика пассажиров, v — успешные валидации интервала, k — число пассажиров, оплаченных валидацией (по умолчанию 1). Интервал помечается недостоверным, если в нём хотя бы один валидатор был недоступен для наблюдения или неисправен.

**Границы работы.** В состав ТЗ входят сбор и разбор трафика IR, формирование событий валидации, их хранение и передача, а также агрегация с данными счётчика пассажиров. Не входят: сам счётчик пассажиров, серверная аналитика и изменения в ПО АСОП.

## 3. Архитектура

IR-Bridge — служба Linux на вычислителе CAMAI, которая читает копию обмена «контроллер ↔ IR» и превращает его в события валидации.

Режим зеркала — основной: отказ CAMAI не влияет на оплату проезда.

**Режимы получения трафика**

| Режим | Схема | Влияние на АСОП | Применение |
| --- | --- | --- | --- |
| `mirror` (основной) | Порт коммутатора зеркалирует трафик на интерфейс CAMAI; чтение через AF\_PACKET или libpcap | Нет | Управляемый коммутатор с функцией port mirroring |
| `bridge` | Два Ethernet-порта CAMAI в прозрачном мосте Linux (br0) в разрыве линии контроллера; чтение с br0 | При питании CAMAI — нет; при отказе железа линия разорвана | Коммутатор без зеркалирования |
| `proxy` | Контроллер подключается к CAMAI:42616, CAMAI — к IR; побайтная ретрансляция с копией в разборщик | Задержка ≤ 2 мс; при отказе CAMAI валидатор недоступен | Только с письменного согласия перевозчика |
| `pcap-file` | Чтение записи .pcap/.pcapng | Нет | Отладка, регрессионные тесты, разбор инцидентов |

Во всех режимах требуется открытый обмен (порт 42616, TLS отключён). Трафик на порт 42800 (TLS) модуль фиксирует как «зашифрованный сеанс» и помечает валидатор ненаблюдаемым.

Не наблюдается обмен, не выходящий в сеть: IntelliReader как служба на 127.0.0.1 внутри ведущего валидатора VENDOTEK T Full A, если приложение АСОП работает на нём же, а также подключения RS-232 и USB. При обследовании объекта фиксируется, какие валидаторы управляются по Ethernet.

**Состав ПО**

| Компонент | Назначение |
| --- | --- |
| `capture` | Захват кадров Ethernet (TPACKET\_V3, BPF-фильтр `tcp port 42616 or tcp port 42800`), чтение pcap, TCP-прокси |
| `tcp_reasm` | Сборка двунаправленных TCP-потоков по четвёрке, упорядочение по seq, обработка потерь и передач |
| `ir_codec` | Выделение кадров IR, проверка CRC-16/XMODEM, декодирование Protobuf по сгенерированным из .proto классам |
| `correlator` | Сопоставление ответов с командами по MSGID и MODULE в сеансе |
| `detector` | Конечный автомат валидации по каждому валидатору, правила одобрения и отказа |
| `aggregator` | Сопоставление с данными счётчика пассажиров, расчёт по интервалам |
| `store` | Локальная БД SQLite (WAL), очередь неотправленных событий |
| `publisher` | Передача событий в шину CAMAI (MQTT) и по HTTP, локальный REST API состояния |
| `health` | Метрики, статус наблюдаемости валидаторов, systemd watchdog |

## 4. Функциональные требования

Требования пронумерованы (ФТ-…) для ссылок в программе испытаний. Непреложное требование для всех режимов, кроме `proxy`: модуль не отправляет ни одного байта в сторону IR и контроллера.

### 4.1. Захват трафика

- **ФТ-1.1.** Режимы `mirror`, `bridge`, `proxy`, `pcap-file` (разд. 3) выбираются конфигурацией без пересборки.
- **ФТ-1.2.** Захват с интерфейса — AF\_PACKET TPACKET\_V3 (резервно libpcap) в режиме promiscuous, BPF-фильтр по настраиваемым портам IR (по умолчанию 42616 и 42800), поддержка VLAN 802.1Q.
- **ФТ-1.3.** Каждый пакет получает метку времени ядра (CLOCK\_REALTIME, микросекунды). Время системы CAMAI синхронизируется по NTP или GNSS; события содержат признак синхронизации часов.
- **ФТ-1.4.** Режим `proxy`: приём соединений контроллера на заданных локальных портах, соединение с IR по таблице соответствия, побайтная ретрансляция без изменений (TCP\_NODELAY, epoll). Разрыв одной стороны закрывает другую. Разбор выполняется асинхронно и не задерживает ретрансляцию.

### 4.2. Сборка TCP-потоков

- **ФТ-2.1.** Поток идентифицируется четвёркой IP:порт. Сторона с портом IR — валидатор, противоположная — контроллер.
- **ФТ-2.2.** Упорядочение по sequence number, удаление повторных передач, буфер внеочередных сегментов до 64 КиБ на направление, обработка SYN, FIN, RST.
- **ФТ-2.3.** При пропуске данных (потеря пакета на зеркале) поток передаёт разборщику признак разрыва; разборщик синхронизируется по заголовку «IR» и CRC (ФТ-3.3). Потоки, начатые до запуска модуля (без SYN), принимаются с первого увиденного сегмента.
- **ФТ-2.4.** Поток закрывается по FIN/RST или при отсутствии трафика дольше `session_idle_timeout_s` (по умолчанию 120 с).
- **ФТ-2.5.** Соединение на порт TLS (42800) не разбирается: валидатор получает статус `encrypted`, в журнал пишется предупреждение.

### 4.3. Разбор кадров IR

- **ФТ-3.1.** Разбор формата HEADER (0x49 0x52) | LENGTH (BE16) | MSGID | MODULE | TYPE | PAYLOAD | CRC (BE16) по разд. 4 Описания API, потоково, с учётом дробления и склеивания кадров в TCP.
- **ФТ-3.2.** Допустимый LENGTH — от 3 до 4122 (кадр целиком ≤ 4128 байт). CRC-16/XMODEM (poly 0x1021, init 0x0000) считается по байтам от HEADER до конца PAYLOAD.
- **ФТ-3.3.** При недопустимой длине или несовпадении CRC разборщик сдвигается на 1 байт и ищет следующий заголовок; счётчики ошибок ведутся по валидатору.
- **ФТ-3.4.** PAYLOAD декодируется классами, сгенерированными protoc из .proto-файлов производителя без их изменения; версия .proto фиксируется в репозитории. Неизвестные поля (более новая версия протокола) пропускаются.
- **ФТ-3.5.** Выбор типа PAYLOAD:

| TYPE | Направление | Класс Protobuf |
| --- | --- | --- |
| 0x01 Command | контроллер → IR | Обёртка модуля по MODULE: 0x01 Miscellaneous, 0x03 ContactlessLevel1, 0x04 ContactlessLevel2, 0x05 Mifare, 0x0A Gui, 0x0C Complex, 0x0D QrCode, 0x0E Cipurse, 0x10 Turnstile, 0x11 MifareExtended, 0x12 TroikaCard; остальные — без декодирования |
| 0x02 Successful | IR → контроллер | По команде с тем же MSGID и MODULE (ФТ-4.2) |
| 0x03 Failure | IR → контроллер | common.failure.FailureResponse |
| 0x04 Pending | IR → контроллер | Пустой |
| 0x05 Notification | IR → контроллер | common.notification.Notification (MSGID и MODULE = 0x00) |
| 0x06 Control | контроллер → IR | Пустой; отмена текущей команды |

### 4.4. Корреляция и определение успешной валидации

- **ФТ-4.1.** В каждом сеансе ведётся таблица ожидающих команд {MSGID → MODULE, имя поля oneof, время}. Pending продлевает ожидание, финальный ответ (0x02, 0x03) закрывает запись, Control помечает текущую команду отменённой.
- **ФТ-4.2.** Соответствие команда → класс успешного ответа: perform\_transaction → contactless.transaction.TransactionResult; poll\_for\_token → contactless.token.Token; poll\_for\_event → complex.poll.Event; poll\_for\_qrcode → qrcode.event.QrCodeEvent; troika\_av3\_read\_ticket → troika.av3.read\_ticket.Ticket; команды записи и индикации — факт успеха без разбора PAYLOAD.
- **ФТ-4.3.** Если команда не наблюдалась (запуск середине обмена, потеря пакета), успешный ответ модулей 0x04, 0x0C, 0x0D декодируется соответственно как TransactionResult, Event, QrCodeEvent; результат помечается `inferred`. Прочие неопознанные ответы только считаются.
- **ФТ-4.4. Предъявление** — успешный ответ TransactionResult (любой status), Token, Event (contactless\_token, contactless\_txn\_result, qrcode, troika\_ticket) или QrCodeEvent. Повтор с тем же носителем в пределах `same_carrier_merge_ms` (по умолчанию 1500 мс) до решения контроллера объединяется с предыдущим (цепочка «EMV first»: NON\_EMV\_CARD → чтение транспортной карты).
- **ФТ-4.5. Конечный автомат на валидатор:** IDLE → PRESENTED (предъявление) → один из исходов: APPROVED (команда одобрения), REJECTED (команда отказа), NO\_DECISION (истёк `decision_window_ms`, по умолчанию 3000 мс, или новое предъявление другого носителя), ABORTED (разрыв сеанса). Событие формируется по каждому исходу; «успешной валидацией» считается только APPROVED.
- **ФТ-4.6. Правила одобрения и отказа** задаются в конфигурации списком матчеров, проверяемых на командах контроллера в состоянии PRESENTED: `gui_picture` (picture\_id из списка, поиск по всему дереву виджетов show\_screen), `gui_text` (регулярное выражение по тексту виджетов Text/GeneratedText, в том числе в complex on\_event\_ui\_action), `gui_customer_picture` (имя картинки), `leds` (green = true при red ≠ true), `rgb_color` (цвет с допуском), `turnstile_pass`. Умолчания: одобрение — APPROVED, APPROVED\_DISCOUNT, зелёный светодиод, allow\_one\_pass; отказ — REJECTED, красный светодиод. По флагу `require_ack` команда индикации учитывается только после успешного ответа IR.
- **ФТ-4.7. Политика успеха** `success_policy`: `indication` (по умолчанию, только команда одобрения); `indication_or_write` (или успешная запись на транспортную карту без последующего отказа); `emv_status` (для АСОП, передающих PerformTransaction с indication = FULL: статусы 0 и 1 без последующего отказа). Наблюдаемое значение поля indication записывается в событие.
- **ФТ-4.8.** Число оплаченных пассажиров k = 1; если регулярное выражение `gui_text` содержит группу захвата, k берётся из первой группы (1–10). Регулярные выражения — std::regex (ECMAScript); при `icase: true` текст и шаблон приводятся к нижнему регистру по UTF-8 (включая кириллицу) и сравниваются как std::wstring.

### 4.5. Носитель и защита данных карты

- **ФТ-5.1.** Идентификатор носителя `carrier_hash` = первые 16 байт HMAC-SHA256(секрет устройства, pan\_hash, а при его отсутствии token.id или SHA-256 данных QR-кода), hex. Секрет создаётся при установке, хранится с правами 0600 и ротируется по конфигурации.
- **ФТ-5.2.** PAN, теги 57, 5A, 5F20, 56, 9F6B, masked\_pan, encrypted\_sensitive\_data, содержимое блоков Mifare и данные QR-кода не записываются на диск, в журналы и не передаются; буферы с ними обнуляются после разбора.
- **ФТ-5.3.** Класс носителя: `bank_card`, `mobile_wallet` (по token\_carrier\_type), `transport_card` (NON\_EMV\_CARD, Mifare/CIPURSE), `troika`, `qr`, `unknown`. Платёжная система — по префиксу AID (тег 84/9F06): A000000658 МИР, A000000003 Visa, A000000004 Mastercard, A000000333 UnionPay.
- **ФТ-5.4.** Запись сырого трафика (pcap) выключена по умолчанию, так как содержит данные карт; включается только на время пусконаладки, с ограничением объёма и срока хранения.

### 4.6. Валидаторы и их состояние

- **ФТ-6.1.** Валидатор определяется по IP-адресу IR; конфигурация сопоставляет ему validator\_id и door\_id. Неизвестный IP регистрируется автоматически со статусом `unmapped`. Дополнительно из PerformTransaction извлекается terminal\_identification (9F1C).
- **ФТ-6.2.** Статус валидатора: `observed` (есть корректный трафик не старше `silence_timeout_s`, по умолчанию 30 с), `silent`, `encrypted`, `faulty` (доля ошибок CRC или FailureResponse выше порога, экран ERROR, отказ самотеста). Переходы статуса публикуются как события.
- **ФТ-6.3.** Из наблюдаемых ответов read\_device\_info и get\_device\_statistic извлекаются версия ПО и события IR (DEVICE\_REBOOT, CONTROLLER\_BECAME\_UNREACHABLE и др.).

### 4.7. Сопоставление со счётчиком пассажиров

- **ФТ-7.1.** Модуль получает события счётчика пассажиров (дверь, время, вошло, вышло) и события открытия/закрытия дверей или остановок из шины CAMAI (MQTT).
- **ФТ-7.2.** Интервал учёта — от открытия первой двери на остановке до закрытия последней плюс `post_close_tail_s` (по умолчанию 120 с): пассажиры валидируются после отправления. Без сигналов дверей — фиксированные окна `fallback_window_s` (300 с).
- **ФТ-7.3.** Режим привязки `match_scope`: `vehicle` (по умолчанию, все двери и валидаторы суммируются) или `door` (валидаторы двери — с вошедшими через неё).
- **ФТ-7.4.** По каждому интервалу формируется запись fare\_interval (разд. 5) с расчётом по формуле разд. 2 и признаком достоверности `reliable` = false, если в интервале любой валидатор был не в статусе observed или счётчик пассажиров сообщил о сбое.

### 4.8. Хранение и передача

- **ФТ-8.1.** События и интервалы записываются в SQLite (режим WAL) до публикации. Хранение: события — 30 суток, интервалы — 90 суток; буфер неотправленного — не менее 72 ч работы без связи.
- **ФТ-8.2.** Доставка «хотя бы один раз»: MQTT QoS 1, уникальный event\_id (UUIDv7) для дедупликации на приёмной стороне, повтор с экспоненциальной задержкой до 60 с.
- **ФТ-8.3.** Локальный HTTP API и метрики Prometheus — по разд. 5.

**5.2. Интервал учёта `fare_interval`:** interval\_id, vehicle\_id, scope (vehicle | door), door\_id, stop\_id (если передан шиной CAMAI), ts\_start, ts\_end, boarded, alighted, validations\_approved, passengers\_paid (Σk), validations\_rejected, no\_decision, unpaid\_estimate, reliable, unreliable\_reasons\[\].

**5.3. Состояние валидатора `validator_status`:** validator\_id, ip, status (observed | silent | encrypted | faulty | unmapped), since, last\_frame\_ts, crc\_errors, failures, ir\_version.

**5.4. Интерфейсы**

| Канал | Адрес | Содержимое |
| --- | --- | --- |
| MQTT, QoS 1 | `camai/{vehicle_id}/fare/validation` | События 5.1 |
| MQTT, QoS 1 | `camai/{vehicle_id}/fare/interval` | Интервалы 5.2 |
| MQTT, QoS 1, retained | `camai/{vehicle_id}/fare/validator/{validator_id}` | Состояние 5.3 |
| MQTT, подписка | `camai/{vehicle_id}/pax/count`, `camai/{vehicle_id}/doors` | Входные данные счётчика и дверей (формат — по стандарту шины CAMAI) |
| HTTP GET | `/api/v1/health` | Статус службы, режим, аптайм, версия |
| HTTP GET | `/api/v1/validators` | Список 5.3 |
| HTTP GET | `/api/v1/events?since=<ts>&limit=<n>` | События 5.1 из локальной БД |
| HTTP GET | `/api/v1/intervals?since=<ts>` | Интервалы 5.2 |
| HTTP GET | `/metrics` | Метрики Prometheus: кадры, ошибки CRC, потери, события по исходам, очередь |

HTTP-сервер слушает 127.0.0.1 и служебный интерфейс CAMAI, но не интерфейс зеркала.

## 6. Нефункциональные требования

**6.1. Платформа и сборка**

| Параметр | Требование |
| --- | --- |
| Аппаратура | Rockchip RK3588, aarch64; два интерфейса Ethernet для режима `bridge` |
| ОС | Linux BSP Rockchip (ядро 5.10 или 6.1), Debian 11/12 или Ubuntu 22.04 arm64; systemd |
| Язык | C++17, компилятор GCC ≥ 10 (aarch64-linux-gnu), флаги `-O2 -march=armv8.2-a -Wall -Wextra -Werror` |
| Сборка | CMake ≥ 3.16; нативная на устройстве и кросс-сборка с x86\_64 через toolchain-файл; пакет .deb |
| Зависимости | protobuf ≥ 3.12 (синтаксис proto2) и protoc, libpcap (опционально), SQLite3, OpenSSL (HMAC-SHA256), Eclipse Paho MQTT C/C++ или libmosquitto, nlohmann/json, yaml-cpp, spdlog, cpp-httplib, GoogleTest; только свободные лицензии (MIT, BSD, Apache 2.0, EPL) |
| Файлы .proto | Каталог `third_party/intellireader-proto/` без изменений; генерация C++ из CMake. Условия распространения .proto согласуются с ООО «МУЛЬТИПАС» |

**6.2. Производительность и ресурсы**

| Показатель | Значение |
| --- | --- |
| Валидаторов на один экземпляр | до 16 |
| Поток кадров IR | до 200 кадров/с на валидатор без потерь |
| Задержка от решения контроллера до публикации | ≤ 500 мс при наличии связи |
| Задержка, вносимая режимом `proxy` | ≤ 2 мс на кадр (99-й перцентиль) |
| Загрузка CPU | ≤ 5 % одного ядра Cortex-A55 в среднем; привязка к ядрам A55 (по умолчанию 0–3), чтобы не мешать видеоаналитике и NPU |
| Память | RSS ≤ 64 МБ |
| Запись на eMMC | Батчи не чаще 1 раза в секунду; объём БД ≤ 512 МБ |
| Время запуска | ≤ 2 с до готовности к захвату |

**6.3. Надёжность**

- Служба systemd `camai-irbridge.service`: Restart=always, WatchdogSec=30 с уведомлениями sd\_notify, корректное завершение по SIGTERM с сохранением очереди, перечитывание конфигурации по SIGHUP без потери сеансов.
- Любые повреждённые или враждебные данные на входе не приводят к аварийному завершению: разборщик и декодер проходят фаззинг libFuzzer не менее 1 ч без находок; сборка CI с AddressSanitizer и UBSan.
- Режим `proxy`: при остановке службы или перегрузке очереди разбора ретрансляция продолжается, разбор пропускается.

**6.4. Безопасность**

- Процесс работает от выделенного пользователя с capabilities CAP\_NET\_RAW и CAP\_NET\_ADMIN, без root.
- Данные карт защищаются по ФТ-5.1–5.4. Интерфейс зеркала не имеет IP-адреса и служит только для приёма.
- MQTT поддерживает TLS и аутентификацию по логину или сертификату.
- Журналы — journald, уровни trace…error; на уровне info и выше нет содержимого PAYLOAD.

**6.5. Качество кода**

- clang-format и clang-tidy в CI; RAII, без сырых new/delete; исключения не пересекают границы потоков.
- Покрытие модульными тестами ≥ 80 % строк для `ir_codec`, `tcp_reasm`, `correlator`, `detector`, `aggregator`.
- Разборщик, детектор и агрегатор не зависят от сети и тестируются на x86\_64 с виртуальными часами.

## 7. Конфигурация

Конфигурация — файл YAML `/etc/camai/irbridge.yaml`; все параметры имеют умолчания, обязательны vehicle\_id и режим захвата. При запуске файл проверяется; ошибка валидации останавливает запуск с понятным сообщением (ключ `--check-config`).

  mode: mirror            # mirror | bridge | proxy | pcap-file
  interface: eth1         # mirror: интерфейс зеркала; bridge: br0
  ir_ports: [42616]
  tls_ports: [42800]
  pcap_file: null
  proxy:
    listen: []            # [{listen: "0.0.0.0:42616", upstream: "10.42.0.12:42616"}]
  cpu_affinity: [0, 1, 2, 3]
validators:
  - {ip: 10.42.0.11, validator_id: V1, door_id: D1}
  - {ip: 10.42.0.12, validator_id: V2, door_id: D2}
session:
  idle_timeout_s: 120
  silence_timeout_s: 30
detector:
  success_policy: indication   # indication | indication_or_write | emv_status
  decision_window_ms: 3000

  approve:
    - {type: gui_picture, ids: [APPROVED, APPROVED_DISCOUNT]}
    - {type: leds, green: true}

    - {type: gui_picture, ids: [REJECTED]}

  match_scope: vehicle    # vehicle | door

  secret_file: /var/lib/camai/irbridge/secret.key

mqtt:
  url: tcp://127.0.0.1:1883
  client_id: irbridge-bus-1042

## 8. Испытания, приёмка и результаты

**8.1. Контрольные векторы из спецификации** (CRC перепроверены расчётом) — обязательный модульный тест `ir_codec`:

| Кадр (hex) | Смысл |
| --- | --- |
| `4952 0007 01 01 01 0A020801 09DF` | Command, Miscellaneous.set\_leds\_state { blue: true } |
| `4952 0003 01 01 02 B26B` | Successful response без PAYLOAD |
| `4952 0003 02 03 04 ED9F` | Pending, модуль 0x03 |
| `4952 0005 01 03 03 080D AA1F` | Failure, error = CARD\_TIMEOUT (13) |
| `4952 0003 00 00 06 F6EE` | Control, отмена |
| `4952 000F 01 01 01 420A1A08616E797468696E67 5025` | Command get\_echo { data: "anything" } |
| `4952 000D 01 01 02 0A08616E797468696E67 0901` | Successful response echo |

**8.2. Виды испытаний**

| Вид | Содержание | Критерий приёмки |
| --- | --- | --- |
| Модульные | Векторы 8.1; дробление кадра на каждой границе байта; склеивание кадров; мусор и искажённая CRC; переход MSGID 255 → 0; Pending и отмена; сценарии детектора (банковская карта одобрена и отклонена, транспортная карта с записью, QR-код, нет решения, две карты подряд, запуск середине сеанса) | Все тесты проходят; покрытие по п. 6.5 |
| Фаззинг | libFuzzer на `ir_codec` и `tcp_reasm` | 1 ч без сбоев и ошибок ASan/UBSan |
| Воспроизведение pcap | Записи стенда (VENDOTEK T + демо-контроллер irc.py или IntelliReader Manager) с протоколом ожидаемых событий | Выход совпадает с эталоном побайтно (без event\_id и меток времени) |
| Стендовые с АСОП | Не менее 500 предъявлений по сценарию (одобрение, отказ по стоп-листу, тайм-аут, транспортные карты, мобильные кошельки) с ведением ручного протокола | Одобрения распознаны ≥ 99,5 %; ложных одобрений 0 |
| Нагрузочные | 16 валидаторов из синтетического pcap с tcpreplay на RK3588, 8 ч | Показатели п. 6.2 |
| Безопасность данных | Поиск последовательностей 13–19 цифр, проходящих проверку Луна, в БД, журналах и MQTT после стендовых испытаний | Не найдено ни одного PAN |
| Опытная эксплуатация | Не менее 5 рабочих дней на ТС; сверка с выгрузкой транзакций АСОП; сравнение unpaid\_estimate с ручным контролем не менее чем на 50 остановках | Расхождение с АСОП ≤ 0,5 % событий; ошибка unpaid\_estimate в пределах погрешности счётчика пассажиров |

**8.3. Этапы**

1. Кодек IR, сборка TCP, режим `pcap-file`, модульные тесты и фаззинг.
2. Корреляция, детектор, хранилище, режимы `mirror` и `bridge`.
3. Агрегатор, MQTT и HTTP, режим `proxy`, пакет .deb.
4. Стендовые испытания, запись эталонного трафика АСОП заказчика, настройка правил одобрения, опытная эксплуатация.

**8.4. Результаты работ**

- Исходный код в репозитории CAMAI, скрипты сборки и CI.
- Пакет `camai-irbridge_<версия>_arm64.deb` с unit-файлом systemd и примером конфигурации.
- Набор обезличенных pcap-записей с эталонными результатами.
- Описание работы ПО (руководство по установке, настройке и эксплуатации).
- Протоколы испытаний по п. 8.2.
